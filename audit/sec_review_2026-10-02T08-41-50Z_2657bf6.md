## Findings

### Finding 1: Batch payment approves an allowance built from sender-controlled decimals and amount — `frontend/src/page/ReceivedInvoice.jsx:326`

- Severity: High
- Confidence: 0.8
- Category: untrusted_input_to_transaction
- Description: `getGroupedInvoices()` takes the group's decimals from `invoice.paymentToken?.decimals || 18` (line 326). The batch payment then builds the allowance with `ethers.parseUnits(invoice.amountDue, decimals)` (lines 625-628) and calls `approve(contractAddress, totalAmount)` (lines 653-656). Both `amountDue` and `paymentToken.decimals` come from the relay payload, which the invoice sender writes.

  `verifyInvoiceHash` (line 770) proves only that the payload matches the hash the sender committed on-chain. It does not prove the payload agrees with the on-chain `amountDue` (`invoice[3]`) or `tokenAddress` (`invoice[4]`). The token-list override at line 814 cannot fix this, because `useTokenList` (`frontend/src/hooks/useTokenList.js:68-73`) drops `decimals`. `BatchPayment.jsx:190-195` has an on-chain decimals check, but this page does not. The contract pulls the real on-chain `amountDue` and only needs the allowance to cover it (`contracts/src/Chainvoice.sol:347-353`).
- Exploit Scenario:
  1. The attacker creates an on-chain invoice to the victim for 10,000 USDC (6 decimals).
  2. The attacker commits and relays a payload with `amountDue: "0.01"` and `decimals: 18`. The UI shows a verified invoice for 0.01 USDC.
  3. The victim pays it in a batch. The app requests an approval of 1e16 base units, and `payInvoicesBatch` transfers the full 10,000 USDC. The rest of the allowance stays in place.
- Recommendation: Build every transaction from on-chain data: `invoice[3]`, `invoice[4]`, and `decimals()` read from the token contract. Reject any payload whose `amountDue` or token disagrees with the chain, and treat it as a hash mismatch. Approve exactly the sum of the on-chain amounts.

### Finding 2: PR previews built from fork code are served on the production origin — `.github/workflows/pr-deploy.yml:196`

- Severity: High
- Confidence: 0.85
- Category: ci_cd / origin_isolation
- Description: `pr-build.yml` builds PR code, including code from forks. `pr-deploy.yml` publishes that build to `gh-pages` under `pr-preview/pr-<n>/`. The same branch serves production at `chainvoice.stability.nexus` (`deploy.yml` writes the CNAME). So preview JavaScript shares production's origin: IndexedDB (decrypted invoices), sessionStorage (the messaging private key, see Note 1), the wallet's connected-site permission, and the domain shown in wallet prompts.
- Exploit Scenario: A fork PR adds code that exports IndexedDB and asks the user to sign the key-derivation message. The bot posts the preview link, and the attacker sends it to users. The link is on the real domain, so the wallet is already connected and the signature prompt shows the trusted origin.
- Recommendation: Serve previews from a separate origin, such as a separate Pages repository or project or a different domain. Alternatively, publish previews only for same-repository PRs or after a maintainer adds a label. Require approval for every fork workflow run.

### Finding 3: Hash-verified payload replaces the on-chain sender, amount and token in what the UI shows and pays — `frontend/src/page/ReceivedInvoice.jsx:773`

- Severity: Medium
- Confidence: 0.8
- Category: data_integrity / spoofing
- Description: Once the payload verifies, `parsed = { ...localInv.data }` becomes the invoice record. The on-chain `from`, `amountDue` and `tokenAddress` are then ignored:
  - The sender's name and address shown in the UI come from the payload (lines 1664, 1692-1694, 2128-2132).
  - `storeRelayInvoice` stores `from: envelope.data.user.address` (lines 930, 963).
  - Single pay skips the approval whenever the existing allowance covers the payload amount (line 508), while the contract pulls the on-chain amount.
  
  The same pattern appears in `SentInvoice.jsx:212` and `BatchPayment.jsx:387-388`.
- Exploit Scenario: The attacker invoices 5,000 USDC on-chain, with a payload claiming the invoice is from "Acme Corp" (Acme's address) for 50 USDC. A victim with a leftover allowance pays and loses 5,000 USDC. Even without a leftover allowance, the false identity can trick victims into paying.
- Recommendation: After the hash check, require the payload's `user.address`, `client.address`, `paymentToken.address` and `amountDue` (parsed with on-chain decimals) to equal the on-chain fields. Always display and pay from the on-chain fields.

### Finding 4: Messaging-key derivation message is not bound to an origin and cannot be rotated — `frontend/src/services/relay/relayKeyManager.js:13`

- Severity: Medium
- Confidence: 0.75
- Category: cryptography / signature_phishing
- Description: The ECIES private key is `keccak256(signMessage("ChainVoice Messaging Key Derivation v2"))`. The message has no domain, address, nonce or warning. One leaked signature therefore reveals the user's permanent decryption key. The derivation is deterministic, so the only way to rotate is to bump the message version.
- Exploit Scenario: A phishing site, or the same-origin preview from Finding 2, asks the user to sign the exact string. The attacker derives the key and decrypts the victim's relay mailbox, both what is already stored and what arrives later.
- Recommendation: Include an explicit warning, the origin and the address in the message (EIP-4361 style or EIP-712). Better, generate a random messaging key and store it wrapped under a wallet-derived key, and provide a rotation path.

### Finding 5: Tokens without a return value (e.g. USDT) can be invoiced but never paid — `contracts/src/Chainvoice.sol:282`

- Severity: Low
- Confidence: 0.9
- Category: token_standards
- Description: `transferFrom` is called through an interface that expects a `bool` return (lines 282, 353). Solidity 0.8 reverts when the return data is empty, so payments in such tokens always revert. Create-time validation only checks `balanceOf` and `allowance`, so these invoices can still be created.
- Exploit Scenario: A user issues an invoice in USDT. Every payment attempt reverts, and in a batch one such invoice makes the whole batch revert.
- Recommendation: Use OpenZeppelin `SafeERC20.safeTransferFrom`, or a low-level call that accepts an empty return. Add tests with a token that returns nothing (issue #86).

### Finding 6: Fee-on-transfer tokens mark an invoice paid while the issuer receives less — `contracts/src/Chainvoice.sol:282`

- Severity: Low
- Confidence: 0.75
- Category: token_standards / accounting
- Description: `isPaid` is set without checking how much actually arrived. A token that charges a transfer fee, or later switches one on (USDT has a dormant `basisPointsRate`), leaves the issuer underpaid while the record shows the invoice settled.
- Exploit Scenario: The issuer invoices 10,000 units of a token that later enables a 1% transfer fee. The issuer receives 9,900, but the invoice shows as paid in full.
- Recommendation: Measure the issuer's balance before and after the transfer and revert if it rose by less than `amountDue`, in both the single and batch paths.

### Finding 7: Unpaginated getReceivedInvoices can be permanently broken for an address by free invoice spam — `contracts/src/Chainvoice.sol:404`

- Severity: Low
- Confidence: 0.7
- Category: denial_of_service
- Description: Creating an invoice is free, and the batch function allows up to 50 per transaction. Each invoice appends to `receivedInvoices[to]`, and nothing removes entries. `getReceivedInvoices` returns the whole array, and the frontend depends on that (`ReceivedInvoice.jsx:729`, `BatchPayment.jsx:346`). Once the array is too large, the `eth_call` hits RPC limits and the victim's dashboard fails to load for good.
- Exploit Scenario: The attacker scripts `createInvoicesBatch` calls targeting the victim with 1-wei invoices until the view call fails.
- Recommendation: Add paginated views plus a count function (PR #227), switch the frontend to them, and consider an anti-spam fee at creation time.

## Notes

### Note 1: Messaging private key kept in sessionStorage by default — `frontend/src/services/relay/relayKeyManager.js:179`

- Category: design-tradeoff
- Observation: The derived key is stored in hex in sessionStorage, where any same-origin script can read it.
- Rationale: This is documented in `useRelayKeys.js:29-33`: the key survives a reload, is cleared when the tab closes, and is wiped when the account changes. No XSS sink was found in the app. The real exposure is Finding 2.

### Note 2: Relay API key is inlined into the bundle — `frontend/src/services/relay/relayClient.js:64`

- Category: accepted-risk
- Observation: `VITE_RELAY_API_KEY` ships to every browser.
- Rationale: This is explicitly documented as not secret in `.env.example`, `README.md` and `deploy.yml`.

### Note 3: Relay mailbox is unauthenticated and world-writable — `frontend/src/services/relay/relayInvoiceMessaging.js:101`

- Category: design-tradeoff
- Observation: Anyone can post envelopes that claim any sender.
- Rationale: This is documented. Payloads are checked against the on-chain `invoiceDataHash` before they are trusted. That stops strangers, but not a malicious sender (Findings 1 and 3).

### Note 4: Public-key registry does not bind the key to the caller's address — `contracts/src/Chainvoice.sol:127`

- Category: design-tradeoff
- Observation: Only the length and the `0x04` prefix are checked. No on-curve check is done, and the key is not tied to the sender's address. Users can rotate their key freely. No one can overwrite another user's entry.
- Rationale: The NatSpec (lines 122-126) describes this as a separate messaging key, and `testUpdatePublicKey` treats rotation as intended.

### Note 5: Unsalted keccak256 payload commitment — `contracts/src/Chainvoice.sol:57`

- Category: design-tradeoff
- Observation: Anyone who can guess the full payload can confirm the guess against the chain.
- Rationale: Payloads are deliberately kept off-chain and encrypted (README, Deployments.md), and they contain many free-form fields. Adding a salt in the frontend would be cheap hardening.

### Note 6: Owner-controlled fee; permissionless withdrawFees — `contracts/src/Chainvoice.sol:453`

- Category: accepted-risk
- Observation: `setFeeAmount` has no upper bound. `withdrawFees` sends only to the treasury and follows checks-effects-interactions (CEI). Because payment requires `msg.value == amount + fee` exactly, a fee change makes the transaction revert rather than overcharge.
- Rationale: Fee management is a documented feature. Reentrancy, double payment, paying a cancelled invoice and self-invoicing are all guarded.

### Note 7: solc 0.8.13 known bugs — none reachable — `contracts/foundry.toml:5`

- Category: compiler
- Observation: The DirtyBytesArrayToStorage pattern is present at line 129, but it is not triggerable because there is no `.push()` and no assembly. The other 0.8.13 bugs need constructs this code doesn't use.
- Rationale: Not exploitable. A compiler bump is still advised, with `evm_version` pinned for ETC compatibility.

## Limitations

**Standing limitations**

- This review does not replace a full manual audit or a penetration test.
- This is static analysis of source text. Nothing was executed, fuzzed, or traced at runtime, so timing-dependent, load-dependent, or infrastructure-dependent issues cannot be confirmed here.
- Confidence scores are the reviewing model's own self-assessment, not a calibrated statistical probability.
- Absence of a reported finding does not mean the code is secure. Safety guardrails built into some models can cause a real vulnerability to be softened, generalized, or left out rather than reported in exploit-level detail, and training-data bias can make some vulnerability classes easier for a model to recognize than others. Treat this report as a floor on what a full audit would find, not a ceiling.
- Findings reflect the reviewing model's training data cutoff. A vulnerability tied to a very recently disclosed CVE or library advisory may not be recognized as such.

**Review-specific limitations**

- Third-party library source was not reviewed: `@aossie-org/idb-backup`, `@aossie-org/thrubox-client`, `eciesjs`, `jspdf`, `pdf-lib`, `jszip`.
- `.github/workflows/track-contributor-prs.yml` passes the PR title and `GIST_PAT` to the external reusable workflow `StabilityNexus/ContributorAutomation`. Possible script injection there could not be checked.
- Unknowns: repo settings for fork-workflow approval, the ThruBox server's access control on `receive`, and Pages response headers (CSP).
- Large page components were partly checked by searching for sinks rather than reading line by line: the rendering parts of `ReceivedInvoice.jsx`, and all of `CreateInvoicesBatch.jsx`.
- `forge build` / `forge test` were not run. The ETC opcode-support facts (PUSH0 since Spiral, no Cancun opcodes) come from documentation and should be confirmed before deploying.
- No content was held back from any finding.

## Remediation status (checked against main `a44ba2c1`, 25 Oct 2026)

All 7 findings are fixed on `main`:

| # | Finding | Fixed by |
|---|---|---|
| 1 | Batch payment approval from sender-controlled values | Invoices are shown and paid from on-chain values (`buildChainInvoice`, `sumBaseUnits`) |
| 2 | PR previews on the production origin | PR #309: previews moved to Cloudflare Pages (`chainvoice-preview.pages.dev`) |
| 3 | Hash-verified payload overrides on-chain sender, amount and token | On-chain display and pay; payload only shown when it matches the record |

Notes 1–7 are informational. Note 5 (unsalted commitment) is the same as peer-audit finding CV-FE-03, acknowledged and deferred until after launch. Note 6 is superseded by the `dev` / `devFee` / `devFeeReceiver` roles (PRs #269, #295).
